# 11. 단위 마법 습득·장착 시스템 개편 (다크소울3 레퍼런스)

> 분류: 기존 확장(`01.UnitSystem`, 07번 단위마법조작시스템의 습득/선택 방식) · 튜토리얼 0~10번 번호 체계와 무관한 별도 개편 작업
> 배경(세션 7 확정): 기존 `UnitCatalogService`의 "해금(Unlock)" 이진 모델과, 그걸 조작하던 테스트 전용 `UnitUnlockTestUIComponent`(고장난 채 방치 — `uiDocument.rootVisualElement`가 null이라 버튼 자체가 생성 안 됨, 이 세션 QA 내내 반복된 경고의 정체)를 **다크소울3식 "습득(소유) → 조건 충족 시 장착(등록)"** 2단계 모델로 교체한다.
> **사용자 확정 사항**:
> - 마법(단위)은 아이템처럼 습득(소유)되고, 조건에 맞는 스탯을 갖고 있으면 인벤토리에서 장착해 사용할 수 있다(다크소울3 마법 시스템 레퍼런스).
> - 장착 조건 미달 시 **장착 자체가 완전히 차단된다**(다크소울3처럼 "장착은 되지만 성능 페널티" 방식이 아님).
> - 장착 슬롯 개수는 **제한 없음** — 보유 중이고 조건을 만족하는 유닛은 전부 장착(=사용 가능) 상태로 둘 수 있다. 다크소울3의 Attunement 슬롯 제한 자체는 채택하지 않는다.
> - 장착/해제는 **아무 때나 인벤토리 메뉴에서** 가능하다(다크소울3의 "모닥불에서만" 같은 장소 제약 없음).
> - **장착 조건이 되는 스탯은 아직 미정이다.** 이 기획서는 "조건 판정 구조가 있다"는 것만 확정하고, 실제 게이팅 스탯(이름/수치)은 추후 논의 후 채운다 — 임의로 확정하지 않는다(코드에서는 항상 통과하는 스텁으로 구현).

## 1. 작업 개요 및 작업 유형 분류
**혼합형**이다.
- 비시청각 요구사항: 유닛(마법)을 "소유(Possessed)"와 "장착(Equipped)" 두 단계로 분리 관리하고, 장착 시도 시 조건(스탯) 충족 여부를 판정해 미달이면 장착 자체를 차단하는 로직을 구현한다.
- 시청각 요구사항: 유저가 인벤토리 메뉴를 열어 소유한 유닛 목록을 확인하고, 조건 충족 유닛은 클릭으로 장착/해제를 토글할 수 있으며, 조건 미달 유닛은 장착 불가 상태(비활성 표시)로 구분된다.

## 2. 유형별 핵심 요구사항
- 서술 공식(비시청각): 기존 `UnitCatalogService`의 단일 "해금" 상태를 "소유"/"장착" 두 개의 독립 상태로 분리하고, 장착 판정에 조건 검사 단계를 끼워 넣어, 습득만으로는 사용 불가능하고 장착까지 마쳐야 퀵슬롯에서 선택 가능하도록 만든다.
- 사용자 조작 결과(시청각): 유저가 인벤토리를 열어(아무 때나) 소유 중인 유닛 아이콘을 클릭하면, 조건을 만족하는 유닛은 즉시 장착/해제되며 장착된 유닛만 실제 전투 중 마우스 휠 퀵슬롯 순환에 나타난다. 조건 미달 유닛은 클릭해도 장착되지 않고 회색으로 표시된다.

## 3. 데이터 정의 및 흐름

**데이터 구조 정의** (근거: `Assets/02.System/01.UnitSystem/01.Logic/UnitCatalogService.cs`/`IUnitCatalogService.cs`, `01.Logic/UnitQuickSlotLogicSystem.cs`, `03.UI/UnitInventoryUIComponent.cs`/`UnitUnlockTestUIComponent.cs` 기존 코드)
- `UnitCatalogService`(기존 파일, 대폭 수정) 내부 상태를 `unlockedUnits(HashSet)` 단일 상태에서 **두 개**로 분리:
  - `possessedUnits(HashSet<PureDataUnit>)` — 습득(소유)한 유닛. 아이템처럼 "갖고는 있지만 아직 못 쓸 수 있는" 상태.
  - `equippedUnits(HashSet<PureDataUnit>)` — 장착(사용 가능) 상태. **슬롯 개수 제한 없음**(사용자 확정) — 조건을 만족하는 만큼 전부 담을 수 있다.
- `IUnitEquipRequirementChecker`(신규 인터페이스, `01.Logic/`) — `bool CanEquip(PureDataUnit unit, out string failReason)`. **1차 구현(`DefaultUnitEquipRequirementChecker`)은 게이팅 스탯이 아직 미정이므로 항상 `true`를 반환하는 스텁**이다 — 스탯이 정해지면 이 클래스 내부 로직만 채우면 되고, `UnitCatalogService`나 UI 쪽은 다시 손댈 필요가 없도록 인터페이스로 분리해둔다.
- `IUnitCatalogService`(기존 파일) 메서드 변경:
  - `void AcquireUnit(PureDataUnit unit)`(신규) — `possessedUnits`에만 추가(자동 장착 안 됨 — 다크소울3처럼 습득≠장착).
  - `bool TryEquipUnit(PureDataUnit unit, out string failReason)`(신규) — 소유 여부 확인 → `IUnitEquipRequirementChecker.CanEquip()` 확인 → 둘 다 통과해야 `equippedUnits`에 추가하고 `true` 반환, 아니면 `failReason`에 사유를 담아 `false` 반환.
  - `void UnequipUnit(PureDataUnit unit)`(신규) — `equippedUnits`에서 제거.
  - `bool IsPossessed(PureDataUnit unit)`(신규), `bool IsEquipped(PureDataUnit unit)`(기존 `IsUnlocked`를 의미에 맞게 이름 변경 — 호출부 전체 갱신 필요).
  - `IReadOnlyList<PureDataUnit> GetPossessedUnits()`(신규, 인벤토리 UI용), `IReadOnlyList<PureDataUnit> GetEquippedUnits()`(기존 `GetUnlockedUnits()`를 이름 변경 — 퀵슬롯 휠 순환이 이 목록을 읽도록 갱신).
  - `event Action<PureDataUnit> OnUnitAcquired`(신규), `event Action<PureDataUnit> OnUnitEquipped`/`OnUnitUnequipped`(기존 `OnUnitUnlocked`를 의미에 맞게 분리).
  - 생성자의 `initialUnits[0]` 자동 습득 로직은 "자동 습득 + 자동 장착"(조건 검사는 스텁이라 항상 통과)으로 유지 — 튜토리얼 시작 시 최소 하나는 바로 쓸 수 있어야 하므로.

**데이터 가공/흐름 서술**
- 필드에서 아이템을 주움(또는 상점 구매 등, 이번 기획서 범위 밖 — 아래 "제외" 참고) → `catalogService.AcquireUnit(unit)` 호출 → `possessedUnits`에 추가, `OnUnitAcquired` 발행 → 인벤토리 UI가 갱신되어 새 아이템이 "미장착" 상태로 나타남.
- 유저가 인벤토리에서 소유 중인 유닛 클릭 → `TryEquipUnit(unit, out reason)` 호출 → `IUnitEquipRequirementChecker.CanEquip()`이 항상 `true`(스텁)이므로 현재는 항상 성공 → `equippedUnits`에 추가 + `OnUnitEquipped` 발행 → `UnitQuickSlotLogicSystem`이 `GetEquippedUnits()`로 순환 대상 목록을 갱신(기존 `GetUnlockedUnits()` 자리를 그대로 대체).
- 이미 장착된 유닛을 다시 클릭 → `UnequipUnit(unit)` → `equippedUnits`에서 제거 → 퀵슬롯 순환 대상에서도 빠짐(현재 선택돼 있었다면 선택 해제 처리 필요 — 구현 시 `RuntimeDataUnitQuickSlot.SelectedUnit`이 방금 해제된 유닛이면 다른 장착 유닛으로 자동 전환하거나 null로 비움, 정확한 동작은 구현 단계에서 UX 관점으로 결정).

**시청각 전달(UX) 서술**
- 인벤토리 메뉴(아무 때나 열림, 여는 입력은 구현 시 기존 프로젝트의 다른 메뉴 여는 방식을 참고해 결정): 소유 중인 유닛을 아이콘 그리드로 표시(기존 `UnitInventoryUIComponent`의 레이아웃 재사용). 장착된 유닛은 강조 테두리, 미장착이지만 장착 가능한 유닛은 기본 표시, 조건 미달 유닛(현재는 스텁이라 발생 안 함, 스탯 확정 후 재검증 필요)은 회색+비활성.
- 실제 전투 중에는 장착된 유닛만 마우스 휠로 순환 가능(기존 `UnitQuickSlotLogicSystem`의 Tactical 컨텍스트 게이트 그대로 재사용).

## 4. DLV 적용 방안 (실제 폴더 경로)

이 작업은 신규 기능이 아니라 **기존 `01.UnitSystem` 확장**이므로 3-2절의 신규 넘버링 규칙은 적용 대상이 아니다.

- **[D] 00.Data** — 변경 없음(`PureDataUnit.cs`에 게이팅 스탯 필드를 추가하는 건 스탯이 확정된 이후의 별도 작업).
- **[L] 01.Logic** — `Assets/02.System/01.UnitSystem/01.Logic/UnitCatalogService.cs`/`IUnitCatalogService.cs`(기존 파일, 3번 절의 메서드/이벤트로 전면 수정), `IUnitEquipRequirementChecker.cs`(신규 인터페이스), `DefaultUnitEquipRequirementChecker.cs`(신규 스텁 구현체) 추가. `UnitQuickSlotLogicSystem.cs`(기존 파일)는 `GetUnlockedUnits()`→`GetEquippedUnits()`, `IsUnlocked`→`IsEquipped`, `OnUnitUnlocked`→`OnUnitEquipped` 등 이름 변경에 맞춰 호출부만 갱신(로직 자체는 변경 없음).
- **[V] 03.UI** — `Assets/02.System/01.UnitSystem/03.UI/UnitInventoryUIComponent.cs`(기존 파일, 현재는 읽기 전용 아이콘 그리드뿐이라 클릭 시 `TryEquipUnit`/`UnequipUnit` 호출하는 상호작용 추가), `UnitUnlockTestUIComponent.cs`(삭제 — 테스트 전용 고장난 코드, 실제 인벤토리 UI로 완전히 대체), `UnitUnlockPopupUIComponent.cs`(기존 파일, `OnUnitUnlocked` 구독부만 `OnUnitAcquired`/`OnUnitEquipped` 중 의미에 맞는 쪽으로 갱신 — "습득 팝업"이면 `OnUnitAcquired`가 맞을 가능성이 높음, 구현 시 확인).
- **기타 호출부 확인 필요**: `catalogService.IsUnlocked`/`GetUnlockedUnits`/`OnUnitUnlocked`를 참조하는 다른 파일(`UnitQuickSlotUIComponent.cs` 등)이 있는지 구현 착수 시 전체 grep으로 재확인하고 전부 갱신할 것.

## 5. 예상 검수 방법 (체크리스트는 §3 데이터 흐름 근거)

- [ ] `AcquireUnit(unit)` 호출 시 `possessedUnits`에만 추가되고 `equippedUnits`(=퀵슬롯 순환 대상)에는 자동으로 들어가지 않는다(습득≠장착).
- [ ] 인벤토리 메뉴에서 소유 중이지만 미장착인 유닛을 클릭하면 `TryEquipUnit`이 호출되어 장착되고, 그 즉시 마우스 휠 퀵슬롯 순환 대상에 나타난다.
- [ ] 이미 장착된 유닛을 다시 클릭하면 `UnequipUnit`으로 해제되고, 퀵슬롯 순환 대상에서 사라진다.
- [ ] 인벤토리 메뉴는 전투 중을 포함해 언제든지 열어서 장착/해제를 변경할 수 있다(사용자가 "아무 때나"라고 확정 — 전투 중 포함 여부가 의도와 다르면 확인 필요).
- [ ] (현재 게이팅 스탯이 스텁이라 재현 불가, 스탯 확정 후 별도 검증) 조건 미달 유닛은 클릭해도 `TryEquipUnit`이 `false`를 반환하며 장착되지 않는다.
- [ ] 씬 시작 시 최초 한 개 유닛은 자동 습득+자동 장착되어(기존 `initialUnits[0]` 로직 유지) 바로 사용 가능한 상태로 시작한다(회귀 없음).
- [ ] 기존 `UnitUnlockTestUIComponent` 삭제 후에도 콘솔에 관련 경고(`UIDocument or rootVisualElement is null`)가 더 이상 발생하지 않는다.

## 6. 정정(세션 8) — 인벤토리는 다크소울3처럼 "여닫는 메뉴"다 (범위 안으로 편입)

최초 작성 시 "인벤토리 메뉴를 여는 입력 바인딩"을 범위 밖으로 뒀으나, **다크소울3 레퍼런스를 그대로 따른다는 원칙(사용자 재확정)에 따라 이번 작업에 포함한다** — 인벤토리는 상시 표시되는 HUD가 아니라, 키로 열고 닫는 별도 메뉴 화면이어야 한다. 세부 디테일(정확한 키, 연출 등)은 나중에 조정될 수 있으나, "메뉴로 여닫는다"는 구조 자체는 지금 구현한다.

**근거 코드(그대로 재사용)**: `Assets/02.System/04.OptionSystem/02.Visualizer/UI/OptionUIComponent.cs`가 이미 이 프로젝트의 표준 "여닫는 메뉴" 패턴이다 — `InputReader`의 토글 이벤트 구독 → `OpenX()`(패널 `DisplayStyle.Flex` + `Time.timeScale=0`(정적 참조 카운트로 다중 인스턴스 안전 처리) + `IInputContextManager.PushContext(UIContext)`) / `CloseX()`(역순 복원), `InputReader` 미주입 시 `Update()`에서 키보드 폴백. 인벤토리도 이 패턴을 그대로 따른다.

**신규 포함 사항**:
- `Assets/Synty/AnimationBaseLocomotion/Samples/Scripts/InputSystem/InputReader.cs`(기존 파일)에 `public Action onInventoryToggled;` 추가, `Update()`에서 `Keyboard.current.iKey.wasPressedThisFrame`(임시 기본 키, 나중에 변경 가능) 시 발행.
- `UnitInventoryUIComponent.cs`를 `OptionUIComponent`와 동일한 구조로 확장 — `[Inject] Construct(IUnitCatalogService, IUnitEquipRequirementChecker, InputReader = null, IInputContextManager = null)`, `ToggleInventory()`/`OpenInventory()`/`CloseInventory()`(패널 표시/숨김 + `Time.timeScale` 정지/복원(자체 정적 참조 카운트, `OptionUIComponent`와는 독립적으로 관리 — 두 메뉴를 동시에 열 때의 상호작용은 이번 범위에서 다루지 않음, 알려진 한계로 남김) + `UIContext` Push/Pop), `Start()`에서 `CloseInventory()`로 시작(기본 닫힌 상태).
- **테스트 편의용 습득 키**(신규 작은 컴포넌트, `UnitDebugAcquireTestComponent.cs` — 이름에 Test를 명시해 실제 게임 기능이 아님을 코드로도 드러냄): 숫자키 1~4를 눌러 인스펙터에 지정된 `PureDataUnit`을 `AcquireUnit()`으로 즉시 습득. 이전의 `UnitUnlockTestUIComponent`와 달리 실제로 동작해야 한다(구현 후 반드시 라이브로 확인).

## 7. 이번 작업 범위 밖 (확정하지 않음, 임의로 채우지 않음)
- **장착 조건이 되는 실제 스탯**(이름, 수치, 어떤 캐릭터 스탯 시스템과 연동할지) — 추후 논의 후 별도 작업으로 `DefaultUnitEquipRequirementChecker`를 실제 구현으로 교체.
- **필드에서 아이템으로 "습득"하는 실제 트리거**(월드 오브젝트 픽업, 상점 구매 등) — 이번 기획서는 `AcquireUnit()` API까지만 정의하고, 실제 게임플레이 트리거(필드 아이템 충돌 등)는 범위 밖. 6절의 테스트용 습득 키가 당분간 그 자리를 대신한다.
- **인벤토리 메뉴의 정확한 열기 키**(현재는 임시로 `I`) 및 연출 디테일 — 나중에 조정 가능, 지금은 구조(메뉴로 여닫힘)만 확정.
- Option 메뉴와 Inventory 메뉴를 동시에 열었을 때의 `Time.timeScale`/입력 컨텍스트 상호작용 — 알려진 한계로 남김, 필요시 별도 작업.
