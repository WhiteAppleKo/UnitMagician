## Goal

공격 파이프라인에서 크리티컬이 **절대 발동하지 않게** 한다. 방법은 **플래그에서 `Critical` 비트를 빼는 것**이다. 스텝 코드(`CriticalStep`), `AttackStepFlags.Critical` 비트, `CombatPipelineManager` 정준 순서 테이블 등록, `DamageContext`의 Crit 필드는 **삭제하지 않고 그대로 둔다**(나중에 특정 무기/버프가 비트를 켜면 다시 동작할 수 있어야 한다).

## 범위

### 포함
1. **조사 먼저**: `AttackStepFlags`/`DefaultAttackFlags`/`CombatFlagState`/`FlagRefCounter`를 쓰는 곳을 전체 grep으로 확인해, 공격 플래그가 결정되는 경로가 `InteractionSystem.DefaultAttackFlags` 하나뿐인지 보고한다(다른 곳에서 `Critical`을 켜는 경로가 있으면 함께 처리하고 보고).
2. **플래그 변경**: `Assets/02.System/03.InteractionSystem/01.Logic/InteractionSystem.cs`의 `DefaultAttackFlags`를 `AttackStepFlags.Critical` → `AttackStepFlags.None`으로 바꾼다. 같은 위치 주석에 "크리티컬은 게임 전체에서 사용하지 않는다. 스텝은 남겨 두고 플래그로만 비활성"을 한 줄 남긴다.
3. **기획서 정정**(문서 수정은 이 Goal 범위에 포함):
   - `Assets/00.Document/02.Tutorial/01.기획문서 초안/00_Overview.md` 53행의 "캐릭터는 회피→방어→치명타→차단→적용 5스텝" 서술을 "치명타 스텝은 코드에 남아 있으나 프로젝트에서 사용하지 않는다(공격 플래그 `None`)"로 정정한다.
   - 04번 문서 2차 게이트 서술과 13번 §0 "3단계 성공 조건" 근처에 "최종 데미지는 크리티컬 없이 결정론적이다(`FinalDamage = 기본 데미지 × 질량 비율`)"를 한 줄 명시한다.
   - `29.Goal프롬프트_수치정합과보스조준및아이템위치.md`는 완료된 이력이므로 본문은 고치지 말고, 맨 위에 "※ 크리티컬 전제는 Goal 30으로 무효(크리티컬 미사용)" 한 줄만 추가한다.
4. **수치 영향 확인(변경 아님)**: 크리티컬이 빠져도 기존 수치(아군 샷 기본 60, 돌문 HP 100, `CoreHitRequiredDamage` 100, 질량 ×2)가 그대로 성립하는지 확인한다 — 얼음만 = 60 < 100, 얼음+크기 ×2 = 120 ≥ 100. 수치를 바꾸지 않는다. 안 맞는 경우만 보고한다.

### 제외 (건드리지 않는다)
- `CriticalStep.cs`, `AttackStepFlags.Critical` 비트, `CombatPipelineManager` 정준 순서 등록, `DamageContext`의 `CritRate`/`CritMultiplier`/`IsCritical`, `CollisionDamageTrigger`의 `critRate`/`critMultiplier` 필드, `DamageFloatingText`의 `[CRITICAL!]` 표시 — **삭제/수정 금지**.
- 투사체 프리팹/씬에 직렬화된 `critRate 0.2`/`critMultiplier 1.5`(`NpcProjectile_Dummy.prefab`, `00.TestScene.unity`) — 플래그가 꺼지면 도달하지 않는 죽은 데이터이므로 **수정하지 말고 위치만 보고**한다.
- 범용 예시 코드(`EvadeStep`, `BlockStep`, `BaseDamagePipeLineSO`, `BaseDamageContext`) 정리, 3단계/돌문 판정 구조 변경(`SizeGate` 추가, 게이트별 결과 플래그 등 — 별도 기획서/Goal), 그 외 모든 시스템.

## 완료 기준
- [ ] 공격 플래그가 결정되는 경로가 조사·보고되었고, 어디서도 `Critical`을 켜지 않는다.
- [ ] `CombatPipelineManager`가 공격 플래그 `None`에 대해 빈 스텝 배열을 조립한다(`[CombatPipelineManager] Attack step cache MISS -> assembled 0 step(s) for flags: None` 로그 또는 `ResolveAttackSteps(None).Length == 0` 직접 확인).
- [ ] Play Mode 실측: 아군→돌문, 아군→보스(1단계 타이머 샷, 3단계 이벤트 투사체), 보스→플레이어 피격 합계 **50회 이상**에서 `IsCritical == false`이고 `RawDamage`가 `baseDamage` 그대로이며(`[InteractionSystem.Damage]` 로그의 `Crit: False`), `[CriticalStep]` 로그가 한 번도 나오지 않는다.
- [ ] 결정론 검증: 얼음만 → 돌문 `cracked but survived`를 20회 반복해도 파괴되지 않고(크리티컬 105 변수 없음), 얼음+크기(kg ×2) → `DESTROYED`. 3단계에서 얼음만/크기만/없음 → `OnCoreHitFail`, 얼음+크기 → `OnCoreHitSuccess`가 10회 이상 반복에서 매번 같은 결과이며 `FinalDamage`가 매번 동일하다(60 → 120).
- [ ] 스텝이 남아 있어 다시 켤 수 있음을 확인한다: `RunFullPipeline(context, AttackStepFlags.Critical, ...)`을 테스트 컨텍스트(`CritRate = 1`)로 직접 호출하면 `CriticalStep`이 여전히 동작한다(검증용 호출이며 코드/에셋에 남기지 않는다).
- [ ] 회귀: 13~15번 흐름(락온마다 팝업, 전환점 1회 발동, 이벤트 중 차단, 풀링 상한, 컨텍스트 스택 `Player` 복귀), `UnitMagicPipeLine` 마법 적용/마나, 콘솔 에러 0건. 디스크에 임시 수치/테스트 코드가 남지 않는다.
- [ ] 기획서 정정 3건(00_Overview, 04/13번, Goal 29 한 줄)이 반영되고, 변경된 파일 목록이 위 범위 안에 있다(`git status`로 확인, 이전 세션 미커밋분과 구분).

1. `unity command recompile` → `recompile_status` + 어셈블리 mtime 교차 확인(스테일 DLL 주의). `clear_console` 후 `console --level error` 0건.
2. Play Mode에서 위 완료 기준을 실측한다(`Time.frameCount`가 멈추면 Game 뷰 포커스 후 입력 주입 또는 리플렉션 직접 호출). 판정 반복은 시드 의존 없이 매번 같은 결과여야 한다.
3. `git diff --stat`/`git status`로 범위를 확인한다(코드 변경은 사실상 `InteractionSystem.cs` 한 줄 + 문서).
