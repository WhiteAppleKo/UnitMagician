## Goal

기존 카메라 시스템(`Assets/02.System/00.Movement/`)에 06번 이벤트 시퀀서 신호로만 트리거되는 신규 카메라 모드 2개(1단계 고정 쿼터뷰, 3단계 이벤트 타겟 추적)와, 그 동안 마우스 회전/줌 입력을 차단하는 신규 입력 컨텍스트를 추가한다.

## 배경 (조사로 확인된 현재 상태)

- `Assets/02.System/00.Movement/00.Data/01.CameraMovement/CameraMode.cs` — 기존 enum `HybridFocus/PlayerOnly/MouseFocus/FirstPerson/ThirdPersonShoulder`.
- `Assets/02.System/00.Movement/01.Logic/01.CameraMovement/CameraFollowService.cs` — `m_strategies`(Dictionary&lt;CameraMode, 전략&gt;) 패턴으로 각 모드별 전략 클래스를 등록·전환(`SetCameraMode`). 152~187행 부근에서 `m_inputContextManager.CurrentContext.ContextType`이 `UI`/`Tactical`이면 마우스 입력 처리를 조기 반환하는 기존 코드가 있음 — 이번 작업은 여기에 `Event` 조건을 추가하는 지점.
- `Assets/02.System/99.Common/Input/IInputContext.cs` — 기존 enum `InputContextType { Player, Tactical, UI }`. `UIInputContext.cs`가 참고할 구현 패턴(단순 상태 클래스, `ContextType`/`TargetCursorLockMode`/`TargetCursorVisible`/`IsActive` + Enter/Exit/Pause/Resume).
- `Assets/02.System/99.Common/Input/IInputContextManager.cs` — `PushContext(IInputContext)`/`PopContext(IInputContext)`.
- 09번 작업(직전 완료)에서 확인된 함정: **VContainer 스코프 트리가 서로 다른 두 시스템을 이어야 할 때는 06의 `bossStatComponent`/09의 `eventSequencerScope` 패턴(인스펙터 직접 참조 + 사후 바인딩)을 그대로 재사용한다.** 이 신규 카메라 트리거 로직도 06(이벤트 시퀀서)의 신호를 구독해야 하므로 같은 문제가 발생할 수 있다 — 씬의 실제 스코프 구조를 먼저 확인해서 `CameraFollowService`가 등록된 스코프와 `EventSequencerSystemLifetimeScope`가 부모-자식으로 연결되어 있는지 확인하고, 안 되어 있으면 09번과 동일한 해법(직접 참조+사후 바인딩)을 적용할 것.

## 범위

### 포함
1. **`CameraMode.cs`(기존 파일) 확장** — `FixedQuarterView`(1단계 퍼즐 고정 쿼터뷰), `EventTargetTracking`(3단계 이벤트 추적) 2개 값 추가.
2. **`InputContextType.cs`(정확히는 `IInputContext.cs`, 기존 파일) 확장** — `Event` 값 추가.
3. **`EventCameraInputContext.cs`(신규, `Assets/02.System/99.Common/Input/`)** — `UIInputContext`와 동일한 구조로 `IInputContext` 구현, `ContextType => InputContextType.Event`, `TargetCursorLockMode => CursorLockMode.Locked`, `TargetCursorVisible => false`.
4. **`FixedQuarterViewCameraStrategy.cs`/`EventTargetTrackingCameraStrategy.cs`(신규, `01.CameraMovement/` 같은 폴더)** — 기존 전략 클래스(`TopViewMouseFocusStrategy` 등)와 동일한 인터페이스를 구현하는 카메라 전략. `FixedQuarterViewCameraStrategy`는 씬에 미리 지정된 고정 좌표/각도로 카메라를 고정. `EventTargetTrackingCameraStrategy`는 두 지점(아군 발사 위치 ~ 보스 위치)을 잇는 구도를 계산.
5. **`CameraFollowService.cs`(기존 파일) 수정** — 마우스 입력 조기 반환 조건에 `InputContextType.Event` 추가(기존 `UI`/`Tactical` 체크와 같은 위치). `m_strategies`에 위 두 신규 전략 등록.
6. **`EventCameraTriggerLogicSystem.cs`(신규, 같은 폴더, 순수 C#)** — 06의 신호(`OnBoss50Percent`에서 `EventTargetTracking` 진입, `OnCoreHitSuccess`/`OnCoreHitFail`에서 원래 모드로 복귀)를 구독해 `cameraFollowService.SetCameraMode(...)` + `inputContextManager.PushContext(new EventCameraInputContext())`/`PopContext(...)`를 호출. 06 스코프와의 연결은 위 "배경"에서 언급한 09번과 동일한 방식(직접 참조+사후 바인딩) 적용.
7. **1단계 고정 쿼터뷰 트리거**: 씬 진입 시(06의 `TutorialStage.Stage1` 초기 상태) `FixedQuarterView` 모드로 시작하도록 배선.

### 제외 (이번 작업 범위 아님)
- 실제 카메라 블렌드 연출(크로스 디졸브/팬 전환 애니메이션, 전환 사운드) — 플레이스홀더(즉시 전환)로 충분, 아트 연출은 범위 밖(10.4절 참고).
- 02(아군NPC)/03(보스AI) 시스템 자체 구현 — 이번 작업은 카메라 트리거 로직까지만, "아군 발사 위치"/"보스 위치"는 씬의 임의 테스트 오브젝트로 대체해 검증(아직 02/03 미구현).
- 이벤트 카메라 종료 신호 누락 시 자동 복구(타임아웃 등 안전장치) — 10.9절이 이미 "이번 보완 범위 밖"으로 남긴 기존 미해결 항목, 임의로 확정하지 않음.

## 검증 절차 (반드시 수행)

1. **컴파일 검증**: `unity command recompile` → `recompile_status` 폴링 + 어셈블리 mtime 교차 확인(스테일 함정, 직접 파일 쓰기 후 `unity command write_text_file` 재기록 고려).
2. **콘솔 에러 확인**: `unity command clear_console` 후 `unity command console --level error`로 에러 0건.
3. **기능 검증(`unity eval`/Play Mode)**:
   - 시나리오 A(씬 진입 초기 모드): Play Mode 진입 직후 `CameraFollowService.CurrentMode == FixedQuarterView` 확인.
   - 시나리오 B(이벤트 카메라 전환): 06의 `OnBoss50Percent`를 실제로 트리거(HP를 50% 이하로) → `CurrentMode == EventTargetTracking`, `IInputContextManager.CurrentContext.ContextType == Event` 확인.
   - 시나리오 C(입력 차단): 위 상태에서 `CameraFollowService.UpdateCameraOffset(마우스 입력, 휠)`을 호출해도 `CurrentLookAngles`/`CurrentZoomSize`가 변하지 않는지 확인.
   - 시나리오 D(복귀): 06의 `OnCoreHitSuccess` 또는 `OnCoreHitFail`을 트리거 → 카메라가 원래 모드로 복귀하고 `Event` 컨텍스트가 pop되어 마우스 입력이 다시 정상 작동하는지 확인.
   - 시나리오 E(회귀): 기존 모드 전환(`SetCameraMode(ThirdPersonShoulder)` 등)과 UI/Tactical 컨텍스트 입력 차단이 여전히 정상 동작하는지 확인.
4. **DLV 준수 자체 점검**: `EventCameraTriggerLogicSystem.cs`에 구체 타입 직접 참조가 있는지 grep, 있다면 그 이유를 보고서에 명시.
5. **범위 확인**: `git status`/`git diff --stat`로 `00.Movement/`, `99.Common/Input/` 외 계획에 없던 파일이 건드려지지 않았는지 확인(06번의 인터페이스 관련 파일은 이미 09번 때 추가됐으므로 재수정 여부만 확인).

모든 항목이 통과하면 이 작업은 완료된 것으로 간주한다.
