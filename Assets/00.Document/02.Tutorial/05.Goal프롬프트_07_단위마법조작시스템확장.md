## Goal

기존 단위(Mass/Volume/Vector) 마법 조작 시스템에 **온도(Temperature) 단위**를 네 번째 단위 타입으로 추가하고, 크기 확대 시 VFX 훅을 추가한다. 얼음 속성은 별도 시스템이 아니라 기존 단위 개념의 연장이며, 락온(조준)은 기존 로직을 그대로 재사용하고 신규 판정 로직을 만들지 않는다.

작업은 코드를 고치는 서브 에이전트와 코드를 평가하는 QA 에이전트로 분리하여 작업한다.

## 배경 (조사로 확인된 현재 상태)

기존 "단위(Unit)" 시스템은 `UnitType`([Flags] enum: `Mass`/`Volume`/`Vector`)마다 `PureDataUnit`(SO, 불변 설정) + `IUnitVisualApplicator`(적용자, 텍스처/스케일 등 실제 변경 로직)를 짝지어 정의하고, 대상 오브젝트는 `RuntimeDataUnitGroup`(어떤 단위를 지원하는지 + 각 단위의 현재 `RuntimeDataUnit` 목록 보관)을 부착해서 참여한다. **`UnitType`을 하나 추가하는 것은 단순히 enum 값 하나 늘리는 게 아니라, 아래 3곳의 하드코딩된 분기를 전부 같이 고쳐야 실제로 동작한다** (하나라도 빠뜨리면 조용히 무동작하거나 잘못된 값이 들어감 — 컴파일 에러가 안 나는 종류의 실수라 특히 주의):

1. `Assets/02.System/01.UnitSystem/00.Data/UnitType.cs` — enum에 새 비트 추가 필요
2. `Assets/02.System/01.UnitSystem/00.Data/RuntimeDataUnitGroup.cs`의 `InitUnits()` — `HasUnit(UnitType.Mass/Volume/Vector)`를 각각 체크해서 초기 `RuntimeDataUnit`을 만드는 if-체인이 하드코딩돼 있다. 새 단위 타입도 여기 분기가 추가돼야, 그 단위를 지원하는 오브젝트가 실제로 해당 `RuntimeDataUnit` 인스턴스를 갖게 된다.
3. `Assets/02.System/01.UnitSystem/01.Logic/UnitBatchCastingService.cs`의 `CalculateNewValue(...)` **그리고** `Assets/02.System/01.UnitSystem/01.Logic/Strategy/TopViewMouseCastingStrategy.cs`의 `CalculateNewValueForUnit(...)` — 둘 다 `spellUnit.UnitType`에 대한 `switch`문이 하드코딩돼 있고 새 타입에 대한 `case`가 없으면 `default: return targetUnit.CurrentValue;`로 떨어져서 "값 변화 없음"이 돼버린다(마나 코스트가 `Mathf.Max(baseCost*0, baseCost)`로 최소 비용만 청구되고, 실제 온도 값은 전혀 안 바뀌는 조용한 버그가 생김).

리뷰로 이미 확정된 사항(재작업 대상 아님):
- 락온/조준 로직(`MagicLockOnComponent`)은 대상이 시간 정지로 완전히 멈춰있음을 전제로 하므로 신규 판정 불필요.
- **중요**: `TopViewMouseCastingStrategy.HandleMouseHoverAndCast()`는 `timeSlowData.IsSlowActive`이면 **즉시 return**해서 시간 정지 중엔 이 전략 자체가 완전히 비활성화된다("전술 명령 시스템에 마우스 입력 전담 양보"). 즉 튜토리얼의 핵심 흐름(시간 정지 중 조준→온도 인챈트→크기 확대)은 실제로는 `TopViewMouseCastingStrategy`가 아니라 **전술 커맨드/배치 캐스팅 경로**(`UnitBatchCastingService`, 06.TacticalCommand 시스템)를 탄다. 그래도 `TopViewMouseCastingStrategy`의 스위치문은 일관성을 위해 같이 고친다(시간 정지 아닐 때의 핀포인트 시전에서도 온도 단위를 쓸 수 있어야 함).
- 데미지 공식은 04번 문서가 `MassUnitApplicatorSO`의 질량 비율(`CurrentValue/OriginalValue`)을 그대로 재사용하기로 확정돼 있으므로, 이 비율 값을 외부에서 읽을 수 있게 공개해야 한다(체크리스트 7.6).

## 범위

### 포함
- `UnitType`에 `Temperature = 1 << 3` 추가
- `PureDataUnit`에 "Temperature Specific Properties" 헤더로 온도 인챈트 목표값 필드 추가(예: `temperatureTarget`, 음수=얼음 방향) — 기존 `MassScaleMultiplier`와 동일한 패턴
- `RuntimeDataUnitGroup.InitUnits()`에 `Temperature` 분기 추가(초기값 0 = 중립)
- `UnitBatchCastingService.CalculateNewValue`와 `TopViewMouseCastingStrategy.CalculateNewValueForUnit` 양쪽에 `case UnitType.Temperature:` 추가(스펠의 `temperatureTarget`을 그대로 반환)
- `TemperatureUnitApplicatorSO : UnitVisualApplicatorSO` 신규 작성 — `Apply(GameObject, RuntimeDataUnit)`에서 `runtimeData.CurrentValue`(온도값)의 부호/크기에 따라 `IUnitTargetVisualizer.ApplyMaterial(...)`로 얼음 머티리얼 교체 + 파티클(서리) 재생. 대상에 `IUnitTargetVisualizer`가 없으면 `MassUnitApplicatorSO`처럼 방어적으로 폴백 처리(예: `MeshRenderer.material` 직접 교체)
- `MassUnitApplicatorSO.Apply`에 VFX 훅 추가 — 스케일 변화가 실제로 일어나는 시점에 마법 링 회전 + 팽창 이펙트 프리팹을 스폰(직렬화 필드로 VFX 프리팹 참조 추가)
- `MassUnitApplicatorSO`가 계산하는 `scaleRatio`(질량 비율)를 외부(04번 파괴 가능 오브젝트 시스템)가 읽을 수 있도록 공개 API로 노출 — 이미 `runtimeData.CurrentValue`/`OriginalValue`가 public이므로 `ratio = CurrentValue/OriginalValue`를 아무 데서나 계산 가능함을 확인하고, 필요하면 이를 계산해주는 정적 헬퍼나 확장 메서드로 정리(중복 계산 방지)
- `PureDataUnit_Temperature`(얼음 인챈트) SO 에셋 인스턴스 1개, `TemperatureUnitApplicatorSO` 에셋 인스턴스 1개 생성해 실제로 연결
- 테스트: 00.TestScene에 `RuntimeDataUnitGroup`(supportedUnits에 Mass+Temperature 포함)을 가진 더미 투사체류 오브젝트로 검증

### 제외 (이번 작업 범위 아님)
- 얼음/불 상성 반응(파지직 이펙트, 상성 판정) — 04번(파괴 가능 오브젝트)/05번(광역 상태이상) 소관
- 실제 아트 리소스(진짜 얼음 텍스처, 파티클, VFX) 제작 — 플레이스홀더(단색 머티리얼, 기본 파티클 프리팹)로 충분
- 크기 확대와 온도 인챈트를 유저가 실제로 조작하는 UI/입력 흐름 전체 재설계 — 기존 퀵슬롯/전술 커맨드 시스템의 기존 입력 경로를 그대로 사용, 새 조작 방식을 만들지 않는다
- 06번(이벤트 시퀀서), 08번(무적 플래그) 등 다른 확장 시스템

- [ ] `MassUnitApplicatorSO.Apply` 호출 시 스케일 변경과 함께 VFX가 스폰된다
- [ ] `MassUnitApplicatorSO`의 질량 비율 값이 외부에서 읽을 수 있는 형태로 노출돼 있다(04번이 나중에 이 값을 그대로 쓸 수 있음을 확인)

## 검증 절차 (반드시 수행)

1. **컴파일 검증**: `unity command recompile` → `unity command recompile_status`가 "completed, no errors"일 때까지 폴링. `Assembly.GetAssembly(type).Location`의 mtime과 소스 mtime을 비교해 실제 반영 여부 재확인(이 프로젝트에서 실제로 겪은 함정 — 단정 금지).
2. **콘솔 에러 확인**: `unity command clear_console` 후 `unity command console --level error`로 에러 0건 확인.
3. **기능 검증 (`unity eval` 위주)**:
   - 시나리오 A(온도 유닛 초기화): `supportedUnits`에 `Temperature`를 포함한 `RuntimeDataUnitGroup`을 가진 오브젝트에서 `GetMatchingUnitData(UnitType.Temperature)`가 `null`이 아니고 `CurrentValue == 0`(중립 초기값)인지 확인.
   - 시나리오 B(온도 인챈트 값 반영): `IUnitChangeService.ChangeUnit(target, temperatureRuntimeData, pureDataUnit_Temperature, calculatedNewValue, ...)`를 직접 호출(또는 `UnitBatchCastingService.ExecuteBatchCast` 경유) → 호출 후 `RuntimeDataUnit.CurrentValue`가 `temperatureTarget`과 일치하는지, `CurrentUnitData`가 온도 SO로 바뀌었는지 확인.
   - 시나리오 C(비주얼 적용): 위 인챈트 직후 대상의 머티리얼이 실제로 교체됐는지(`MeshRenderer.sharedMaterial`/`material` 비교) 확인.
   - 시나리오 D(크기 확대 VFX): `MassUnitApplicatorSO.Apply`를 호출해 스케일이 바뀌는 동시에 VFX 오브젝트가 씬에 스폰되는지 확인.
   - 시나리오 E(회귀): 기존처럼 `Mass`/`Volume`/`Vector` 단위 변경을 호출해 여전히 정상 동작하는지(값 계산 결과가 이번 작업 전과 동일한지) 확인.
4. **범위 확인**: `git status`/`git diff --stat`로 이번 작업이 `01.UnitSystem` 밖의 파일(예: `Assets/PipeLine/`, `Assets/02.System/07.NpcSystem/`)을 건드리지 않았는지 확인.

모든 항목이 통과하면 이 작업은 완료된 것으로 간주한다.
