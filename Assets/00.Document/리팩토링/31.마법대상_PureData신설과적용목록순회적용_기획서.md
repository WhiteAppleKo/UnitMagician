# 31. 마법 대상 PureData 신설 + 적용 마법 목록 순회 적용 (기획서)

> 작성일: 2026-10-20 · 상태: **구현 완료 · QA 합격**(2026-10-20, Goal 58 — 권고 2건 수정 후 재검증 합격) · 구현 세부 §6-A, 남은 결정 §6-B · 실행 Goal: [58번](../02.Tutorial/Goal프롬프트/58.Goal프롬프트_마법대상PureData와순회적용.md)
> 형식: `코드_작업_기획서_가이드라인_v1.0.md`
> 선행: 30번(RuntimeDataUnit 마법 인스턴스화 + 대상 적용 목록, Goal 57 QA 합격, 미커밋). **30번의 대상 상태 설계(`RuntimeDataUnitAttribute`, 원본 값을 컴포넌트 필드·코드 상수에 둔 것)를 이 문서가 대체한다.**
> 사용자 확정(2026-10-19~20):
> - **런타임 상호작용이 필요한 모든 항목은 PureData를 갖고, RuntimeData는 그 PureData를 바탕으로(스탯·장비 등 영향 반영) 초기화·캐싱되는 런타임 상태다**(코드 가이드라인 1-1 [D] "Runtime Data: PureData 읽기 참조"). 마법 대상도 예외가 아니다.
> - 원본 질량을 컴포넌트 필드(`RuntimeDataUnitGroup.bakedMassValue`)에 둔 것은 사용자가 테스트용으로 잠깐 해 둔 임시 코드다.
> - **마법 대상의 RuntimeData**: 대상 PureData 값으로 초기화한다. 적용 마법 목록이 바뀔 때마다 PureData 값으로 되돌린 뒤, **목록을 순서대로 순회하며 마법을 적용**해 모든 마법이 적용된 RuntimeData를 만든다.
> - 적용 목록 누적, 조건 해제 후 앞으로 당김, 같은 속성 곱 배율 합산 후 베이스에 곱하는 규칙(30번)은 그대로 둔다.

---

## 1. 작업 개요 및 유형
**비시청각**(Pure Data / Logic 구조 개편). 유저가 보는 결과(스케일·얼음·데미지·게이트 판정·누적·해제)는 30번 구현과 같아야 한다. 바뀌는 것은 두 가지다.
- 대상 원본 값의 위치가 PureData로 옮겨진다.
- 대상 상태를 "속성 칸마다 따로 계산"하던 방식에서 "PureData로 리셋한 뒤 목록 순회 적용"으로 만든다.

## 2. 핵심 요구사항
1. 마법 대상 PureData(`PureDataUnitTarget`)를 새로 만든다. 지원 속성과 원본 값(질량·온도·Vector 기본 속도)을 이 SO로 옮겨, 컴포넌트 직렬화 필드와 코드 상수에서 원본 값을 없앤다.
2. 대상 RuntimeData(`RuntimeDataUnitTarget`)가 `PureDataUnitTarget`을 읽기 참조하고, 실제 상태 필드(현재 질량·온도·Vector)를 직접 갖게 한다. `RuntimeDataUnitAttribute`(Base/Current 칸)는 삭제한다.
3. 목록이 바뀔 때마다 "PureData 값으로 리셋 → 목록을 처음부터 순서대로 돌며 각 마법의 Applicator가 상태에 적용 → 마무리"로 상태를 다시 만든다. 그 결과로 시각·데미지를 적용해, 대상 상태가 언제나 "PureData + 목록 전체"의 결과가 되게 한다.
4. 같은 재계산 함수를 실제 적용과 미리보기(복사본 상태)가 함께 쓰게 해서, 두 결과가 항상 같게 한다.

- 삭제: `RuntimeDataUnitAttribute.cs`, `RuntimeDataUnitTarget.GetAttribute`/`Attributes`, `RuntimeDataUnitGroup.GetAttribute`.
- **`RuntimeDataUnitGroup`**(MonoBehaviour): `supportedUnits`·`bakedMassValue`·`BakedMassValue`를 지우고 `[SerializeField] PureDataUnitTarget targetData` 하나를 둔다. `InitUnits`는 `new RuntimeDataUnitTarget(targetData)`. `HasUnit`·`SupportedUnits`는 `targetData`에 위임한다. `targetData`가 비어 있으면 경고 후 지원 속성 없음으로 동작한다.

**Applicator (`IUnitApplicator`, 30번 확장 → 순회 적용형으로 변경)**
| 멤버 | 역할 |
|---|---|
| `DataType`, `UnitType`, `CreateInstance` | 30번 그대로(시전자 영향 계산 자리 포함) |
| `void Accumulate(UnitStateAccumulator acc, RuntimeDataUnit instance)` | 순회 중 이 항목을 누적기에 적용(Mass: 배율 합에 더함, Temperature: 목표 온도 설정, Vector: 방향·속도 설정) |
| `void ApplyVisual(UnitApplyTarget target, RuntimeDataUnitTarget state, RuntimeDataUnit added)` | 완성된 상태로 시각 적용. `added`가 이 타입일 때만 이펙트 스폰 |
| `void ApplyDamage(RuntimeDataAttackDamage damage, RuntimeDataUnitTarget state)` | 데미지 계산 자리(기본 비어 있음, Mass만 계산식) |
- 기존 `CalculateValue`·`Calculate`와 30번식 `Apply(target, attribute, applied, added)`는 위 세 멤버로 대체한다.

**`UnitStateAccumulator`** (신규 · 순수 C# · 순회 중 임시 값) — `MassMultiplierSum`(float), `MassEntryCount`(int), `Temperature`(float?), `VectorDirection`/`VectorSpeed`(nullable). 순회가 끝나면 계산기가 이 값으로 상태를 확정한다. 상태(RuntimeData)에 계산 중간값을 두지 않기 위한 Logic 쪽 작업 공간이다.

**`IUnitTargetStateCalculator` / `UnitTargetStateCalculator`** (신규 · 순수 C# · VContainer 등록) — `void Recalculate(RuntimeDataUnitTarget state)`. 실제 적용과 미리보기가 공유하는 단일 재계산 함수다.

### 3-2. 흐름
1. **초기화** — `RuntimeDataUnitGroup.Awake/InitUnits` → `new RuntimeDataUnitTarget(targetData)` → 상태 = PureData 값(질량 = `baseMass`, 온도 = `baseTemperature`, Vector 속도 = `baseVectorSpeed`).
2. **시전** — 30번과 같다(`ChangeUnit` → `CreateInstance` → `AddApplied`). 속성 지원 여부는 `state.HasUnit`.
3. **재계산(`UnitTargetStateCalculator.Recalculate`)** — 목록이 바뀔 때마다:
   1. `state.ResetToData()`
   2. `acc = new UnitStateAccumulator()`; `AppliedUnits`를 **처음부터 순서대로** 돌며 `registry.GetByUnitType(unit.UnitType).Accumulate(acc, unit)`
   3. 확정:
      - 질량 = `MassEntryCount > 0 ? baseMass × MassMultiplierSum : baseMass` → `SetMass`
      - 온도 = `acc.Temperature ?? baseTemperature` → `SetTemperature`. 순서대로 덮어쓰므로 가장 나중 항목의 값이 남는다(30번 §6-2와 같은 결과).
      - Vector = 가장 나중 값, 없으면 기본 → `SetVector`
4. **적용(`UnitApplyLogicSystem`)** — `OnAppliedUnitsChanged(type, added)` → 정적 이벤트 `OnAnyUnitApplyRequested(UnitApplyTarget, RuntimeDataUnitTarget, UnitType changed, RuntimeDataUnit added)` → `Recalculate(state)` → 바뀐 속성의 Applicator로 `ApplyVisual(target, state, added)`. 대상에 `AttackDamage`가 있으면 `damage.SetCurrentDamage(damage.BaseDamage)`로 되돌린 뒤, 대상이 지원하는 속성의 Applicator마다 `ApplyDamage(damage, state)`를 호출한다(계산식이 있는 것은 Mass뿐).
5. **시각·데미지**
   - Mass: 스케일 = `cbrt(state.MassRatio)`로 `ApplyMassScale(state.CurrentMass, …)`. `added`가 Mass일 때 `added.Source`의 VFX 스폰. 데미지 = `RoundToInt(BaseDamage × state.MassRatio)`.
   - Temperature: `state.CurrentTemperature < 0`이면 목록의 가장 나중 Temperature 항목의 `iceMaterial`. `added`가 Temperature일 때 서리 파티클을 `clamp(|온도|/10, 0.5, 3)` 배율로 스폰.
   - Vector: `state.VectorDirection/Speed`로 `ApplyVelocity`(항목이 없으면 건너뜀, 보존용).
6. **해제** — `RemoveApplied`/`RemoveAllOfType` → 바뀐 속성마다 4번 경로(`added = null`이라 이펙트 없음).
7. **판정** — `AttributeGateStep`: `state.HasUnit(Temperature)`가 아니면 실패(기존과 같음), 맞으면 `state.CurrentTemperature`. `SizeGateStep`: `state.HasUnit(Mass) ? state.MassRatio : 1`.
8. **미리보기** — `LockOnPreviewCalculator`: 대상마다 `sim = state.CreateSimulation(큐 마법의 임시 인스턴스들)` → `calculator.Recalculate(sim)` → `sim.CurrentMass`, `sim.MassRatio`, `cbrt(sim.MassRatio)`, `sim.CurrentTemperature`. 실제 상태와 목록은 바뀌지 않는다.
9. **비용** — `CostOfPair`는 `state.HasUnit`. `UnitChangeService` 폴백 비용은 "현재 값 vs 새 인스턴스를 더한 시뮬레이션 값"의 차로 계산한다(30번과 같은 의미).
10. **풀 재사용** — `ResetForReuse` → `state.Reset()`(이벤트 없음).
11. **에디터 툴 `UnitMassBaker`** — 메시 부피로 계산한 질량을 대상의 `PureDataUnitTarget.baseMass`에 기록한다(`SerializedObject`로 에셋 수정, Undo·SetDirty). 같은 에셋을 쓰는 대상들의 계산값이 서로 다르면 경고 로그만 남기고 덮어쓰지 않는다. 씬 dirty 표시는 하지 않는다(에셋만 바뀜).

### 3-3. 시청각
- 30번 구현과 **같다**.
  - kg 1회: 스케일 ×2^(1/3), VFX 1회, 데미지 ×2
  - kg 3회: ×6, 스케일 ×6^(1/3), VFX 3회
  - Frost: 얼음 머티리얼, 파티클 1.5배
  - 해제 시 원복(이펙트 없음)
  - 돌문·보스 판정 결과 동일
- 씬의 TestDummy는 질량 5에서 시작한다(씬 전용 값이 에셋으로 옮겨짐).

## 6. 설계 판단 (사용자 명세 밖 — 기존 동작 유지 기준)
1. 대상 에셋 폴더는 `00.Data/04.Target/`이다(구체 마법 `03.Magic` 다음 번호, 레이어마다 같은 번호 규칙은 Data에만 해당).
2. 대상 에셋은 프리팹 단위로 만든다. Sphere 2개는 같은 프리팹·같은 메시라 하나의 에셋을 공유하고, TestDummy는 씬 전용 값(5)이라 에셋을 따로 둔다.
3. 순회 중간값(배율 합 등)은 RuntimeData가 아니라 Logic의 `UnitStateAccumulator`에 둔다. RuntimeData는 확정된 상태만 갖는다.
4. 시각 적용은 바뀐 속성의 Applicator만 하고, 데미지는 매 재계산마다 기본값으로 되돌린 뒤 모든 계산 자리를 다시 거친다(속성 하나만 바뀌어도 데미지가 다른 속성 결과를 잃지 않게).
5. `Assets/_Recovery/0.unity`(크래시 복구 씬, 미추적)는 수정하지 않는다.

### 6-A. 구현 중 정한 세부 (Goal 58, QA 적합 판정)
- `PureDataUnitTarget`: private 직렬화 필드 + 읽기 전용 프로퍼티(`SupportedUnits`, `BaseMass`, `BaseTemperature`, `BaseVectorSpeed`)와 `HasUnit`.
- `RuntimeDataUnitTarget`
  - `GetApplied(UnitType)`는 유지한다(기즈모 UI가 사용).
  - `CreateSimulation`은 대상이 받을 수 없는 속성의 extra를 제외한다.
  - Data가 없으면 상태 값이 0이고 지원 속성이 없다.
  - Vector 방향의 리셋 값은 zero다.
- Applicator 공개 멤버:
  - `Accumulate`, `ApplyVisual`
  - `int ApplyDamage(int currentDamage, RuntimeDataAttackDamage, RuntimeDataUnitTarget)`: 새 값을 반환한다. 기본은 입력값 그대로이고 Mass는 `currentDamage × MassRatio`다.
  - `float ReadValue(RuntimeDataUnitTarget)`: 이 속성의 현재 값(Mass `CurrentMass`, Temperature `CurrentTemperature`, Vector `VectorSpeed`).
  - 내부 훅은 `AccumulateInstance`, `ApplyVisualToTarget`, `CalculateDamage`, `ReadStateValue`다.
- `UnitApplyLogicSystem`의 데미지 계산은 지역 값 BaseDamage에서 시작해 지원 속성의 Applicator를 차례로 거치고, `SetCurrentDamage`는 한 번만 호출한다. 값이 그대로면 `OnDamageChanged`도 나가지 않는다.
- `UnitChangeService`의 폴백 비용과 `LockOnPreviewCalculator`의 예상 값은 Applicator의 `ReadValue`로 읽는다. 미리보기에 남은 switch는 값을 미리보기 칸에 배치하는 일만 한다.
- `UnitMassBaker`
  - 부피를 계산할 수 없으면 건너뛴다(1.0 하드코딩 삭제).
  - 같은 에셋을 공유하는 대상끼리 값이 다르면(상대 오차 1e-5) 경고만 남긴다.
  - 저장은 에셋에만 한다(`SaveAssetIfDirty`).

### 6-B. 남은 결정 (사용자)
- **`UnitMassBaker`의 부피 합산 범위**: 지금 알고리즘(HEAD와 같음)은 자식 메시와 비활성 자식까지 더한다.
  - 현재 씬 기준 계산값은 Sphere 1.86965036(루트 0.97226 + 자식 Torus 0.896 등), TestDummy 1이다.
  - 에셋 값 0.97226274(루트 메시만 잡혔을 때의 Baker 결과)와 5(손으로 넣은 씬 전용 값)와 다르다.
  - 그래서 메뉴를 실행하면 원본 질량이 덮어써진다.
  - 선택지: 루트 메시(또는 콜라이더)만 계산하도록 바꾸고 비활성 자식은 제외할지, TestDummy처럼 손으로 넣은 값을 Bake 대상에서 뺄지.
- **에디터에 열린 씬의 메모리 상태**: 디스크 파일과 다르다(카메라 FOV·Transform, `volumeColor` 키). 디스크 파일이 올바른 상태다. 씬을 다시 저장하기 전에 디스크에서 다시 불러와야 한다.
