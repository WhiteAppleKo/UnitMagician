# Goal: 공격/피격 파이프라인 분리 리팩토링 (플래그 기반 스텝 해석 + 캐싱)

> 작성일: 2026-09-18
> 이 문서는 대화로 합의된 설계를 그대로 실행 가능한 작업 지시문(prompt)으로 옮긴 것이다. 아래 내용을 그대로 실행하고, 마지막 "검증 절차"까지 통과해야 완료로 간주한다.

## Goal

`Assets/PipeLine/`의 기존 데미지 파이프라인(`CharacterDamagePipeLine`/`DamageContext`)을, **공격 파이프라인(공격자 스탯 기반)과 피격 파이프라인(피격자 스탯 기반)으로 분리**하고, 어떤 스텝을 적용할지를 **공격자/피격자 각자가 들고 있는 플래그**로 결정하며, 그 플래그→스텝 배열 변환을 **세션 내내 유지되는 캐시(메모이제이션)**로 처리하도록 리팩토링한다. 하드웨어 부담(GC 할당, 불필요한 async 오버헤드, 매 타격마다 반복 연산)을 최소화하는 것이 최우선 목표다.


작업은 코드를 고치는 서브 에이전트와 코드를 평가하는 QA에이전트로 분리하여 작업한다.

## 배경 (조사로 확인된 현재 상태)

- `PipeLineSo<T>`/`IPipeLineStep<T>`([PipeLineBase/](Assets/PipeLine/PipeLineBase/PipeLineSO.cs))는 범용 재사용 프레임워크로 **그대로 유지**한다 — 다른 프로젝트/기능에서도 쓸 수 있도록 일반화된 코드이므로 이번 리팩토링 대상이 아니다.
- 현재 `CharacterDamagePipeLine.asset`에는 **`ApplyDamageStep` 하나만** 배선돼 있고, `EvasionStep`/`DefenseStep`/`CriticalStep`은 코드만 있고 실제로는 실행되지 않는다.
- `ApplyDamageStep.Execute`가 `async`+`await UniTask.Yield()`를 써서 실제로 기다릴 게 없는데도 상태 머신 할당과 1프레임 지연을 유발하고 있다.
- `CollisionDamageTrigger`가 충돌마다 `new DamageContext { ... }`로 클래스 인스턴스를 힙 할당한다.
- `BaseDamageContext`/`BaseDamagePipeLineSO`(+중복된 `EvadeStep`/`BlockStep`)는 **의도적으로 남겨둔 예시/템플릿 코드**다 — 이번 작업에서 **수정·삭제하지 말 것**.

## 범위

### 포함
- `DamageContext`를 `class`→`struct`로 전환 (기존 필드 유지 + `HitRegistered`(bool) 필드 추가 — "피격 판정"과 "데미지 판정"을 분리해 기록하기 위함)
- `IDamageable` 인터페이스 신설, `ICharacterStatService`(또는 `CharacterStatComponent`)가 이를 구현/위임하도록 연결
- `AttackStepFlags`([Flags] enum: 우선 `Critical` 비트만), `HitStepFlags`([Flags] enum: 우선 `Evasion`, `Defense` 비트만) 정의 — 향후 다른 시스템(속성 게이트, 크기 게이트 등)이 비트를 추가할 수 있도록 확장 여지를 남길 것
- 플래그를 "추가 카운터"/"강제 제외 카운터"로 관리하는 참조 카운트 컨테이너(예: `FlagRefCounter<TFlags>`) 구현 — 겹치는 버프/무기가 같은 비트를 요구해도 안전하게 add/remove 되도록
- `CombatPipelineManager` 구현: `AttackStepFlags`/`HitStepFlags` → 해석된 `IPipeLineStep<DamageContext>[]`를 `Dictionary`에 캐싱(메모이제이션), 처음 보는 조합일 때만 조립
- 기존 스텝(`EvasionStep`, `DefenseStep`, `CriticalStep`, `ApplyDamageStep`)을 **상태 없는 공유 싱글턴**으로 전환하고, `async`/`await UniTask.Yield()`를 제거해 실제 비동기 작업이 없을 때는 `UniTask.FromResult(context)`를 즉시 반환하도록 수정 (인터페이스 시그니처 `UniTask<T> Execute(T context)` 자체는 그대로 유지)
- `ApplyDamageStep`은 플래그 게이트 대상이 아니라 **파이프라인 종료 시 항상 실행되는 고정 마지막 스텝**으로 취급
- `CollisionDamageTrigger`/`InteractionSystem`이 기존 `CharacterDamagePipeLine` 에셋을 직접 호출하던 것을 `CombatPipelineManager` 경유로 교체

### 제외 (이번 작업 범위 아님)
- `BaseDamageContext`/`BaseDamagePipeLineSO` 및 그 안의 `EvadeStep`/`BlockStep` 수정·삭제
- 파괴 가능 오브젝트(돌문), 보스 무적 플래그, 온도 단위 게이트 등 튜토리얼 전용 시스템(기획 문서 04/05/07/08번) 실제 구현 — 이번 작업은 그 시스템들이 나중에 올라탈 **기반 구조만** 만든다
- `RuntimeStatData`에 실제 "방어력" 스탯 추가(현재 존재하지 않음) — `DamageContext.Defense`는 지금처럼 외부에서 값을 채워주는 필드로만 유지, 실제 방어 스탯 배선은 후속 작업으로 남김
- `UnitMagicPipeLine`(별도 파이프라인) 변경

## 설계 스펙 요약

```
공격 발생
  └ DamageContext(struct) 생성 (Attacker/Victim/RawDamage/CritRate 등 초기값)
  └ CombatPipelineManager.ResolveAttackSteps(attacker.CurrentAttackFlags)
        └ 캐시 히트/미스 처리 (미스 시 1회 조립 후 등록)
  └ 해석된 공격 스텝 배열 순차 실행 (예: CriticalStep) → RawDamage 등 갱신
  └ context.HitRegistered = true 로 설정
  └ CombatPipelineManager.ResolveHitSteps(victim.CurrentHitFlags)
        └ 캐시 히트/미스 처리
  └ 해석된 피격 스텝 배열 순차 실행 (예: EvasionStep → DefenseStep) → FinalDamage/IsEvaded 갱신
  └ ApplyDamageStep(고정, 항상 실행) → 시각 효과 재생 + victim.IDamageable에 결과 전달
```

- 캐시는 `Dictionary<AttackStepFlags, IPipeLineStep<DamageContext>[]>` / `Dictionary<HitStepFlags, IPipeLineStep<DamageContext>[]>` 두 개, `CombatPipelineManager`(VContainer Singleton) 안에 보관 — 세션(앱 라이프사이클) 내내 유지
- 플래그 값은 각 엔티티의 **RuntimeData**(불변 PureData가 아님)에 저장, 버프/무기 장착 시 참조 카운터를 갱신해서 파생시킴

## 검증 절차 (반드시 수행)

1. **컴파일 검증**: `unity command recompile`(강제 트리거) → `unity command recompile_status`를 "completed, no errors"가 뜰 때까지 폴링. 의심스러우면 `Assembly.GetAssembly(type).Location`의 mtime과 소스 파일 mtime을 비교해 실제로 최신 반영됐는지 재확인 (recompile_status 한 번만 찍고 단정하지 말 것 — 프로젝트에 기록된 함정).
2. **콘솔 에러 확인**: `unity command console --level error`로 에러 0건 확인.
3. **기능 검증 (Play Mode 또는 `unity eval`)**:
   - 시나리오 A: 회피율 0인 공격자→방어 0인 피해자 조합으로 공격 → 항상 명중하고 `FinalDamage`가 기대값과 일치.
   - 시나리오 B: 피해자의 회피율을 100%로 설정 → 항상 회피, `FinalDamage` 미적용, HP 불변.
   - 시나리오 C: 공격자의 치명타율을 100%로 설정 → `IsCritical == true`, `RawDamage`가 `CritMultiplier`만큼 증가한 값으로 최종 반영.
   - 시나리오 D: 같은 플래그 조합으로 두 번째 공격 실행 → 캐시가 재조립 없이 재사용되는지(디버그 로그 또는 캐시 크기 변화로) 확인.
   - 시나리오 E: 런타임에 플래그를 변경(예: 버프 부여 시뮬레이션으로 비트 추가) 후 공격 → 새 조합이 새로 캐시에 등록되고 그에 맞는 스텝이 실행되는지 확인.
4. **회귀 확인**: 기존 씬(테스트 씬)에서 플레이어가 일반 공격/투사체로 적을 타격했을 때 HP가 정상적으로 감소하는지 실제 Play Mode에서 눈으로 확인.
5. **범위 확인**: `git diff` 또는 `unity` 도구로 `BaseDamageContext`/`BaseDamagePipeLineSO` 관련 파일이 이번 작업에서 전혀 수정되지 않았음을 확인.

모든 항목이 통과하면 이 작업은 완료된 것으로 간주한다.
