## 2. 문제점 분석 (Code Smells - 5대 기준 위배 상세)

### 2-1. 설계 원칙 위배 (DIP 및 Demeter 법칙)
* **컴포넌트 직접 조작:** `MassUnitApplicatorSO.cs`, `VectorUnitApplicatorSO.cs`, `VolumeUnitApplicatorSO.cs`가 `target.GetComponent<Rigidbody>()`, `target.GetComponent<MeshRenderer>()`, `target.transform.localScale`을 직접 변경함.
* **추상화 부재:** 타겟 객체의 구체적인 내부 구조를 알고 있어야 하므로 대상 오브젝트의 컴포넌트 구조 변경 시 모든 SO가 깨질 위험이 있음.

### 2-2. DLV 아키텍처 위배
* 어플리케이터가 `IUnitTargetVisualizer` 인터페이스를 거치지 않고 게임오브젝트를 직접 조작하여 비주얼 캡슐화가 훼손됨.

## 3. 리팩토링 설계 (To-Be Architecture)

```
[V: Visualizer Layer]
IUnitVisualApplicator (SO Interface)
├── MassUnitApplicatorSO (질량/스케일 연산 후 Visualizer에 전달)
├── VectorUnitApplicatorSO (방향/속도 연산 후 Visualizer에 전달)
└── VolumeUnitApplicatorSO (머티리얼/부피 연산 후 Visualizer에 전달)

IUnitTargetVisualizer (Target Interface)
└── UnitTargetObjectVisualizer (Rigidbody, Transform, MeshRenderer 실제 조작 캡슐화)
```

### 3-1. IUnitTargetVisualizer 인터페이스 기반 위임
* Applicator는 타겟의 `IUnitTargetVisualizer`를 획득하여 고수준 메서드(`ApplyMassScale`, `ApplyVelocity`, `ApplyMaterial`)만 호출.
* 실제 물리/렌더링 프로퍼티 변경은 타겟의 `UnitTargetObjectVisualizer`가 내부에서 안전하게 캡슐화하여 처리.

## 4. 단계별 변경 명세

### Step 1: IUnitTargetVisualizer 인터페이스 확장
* `Assets/02.System/01.UnitSystem/02.Visualizer/IUnitTargetVisualizer.cs`:
  ```csharp
  public interface IUnitTargetVisualizer
  {
      void ApplyMassScale(float mass, float scaleMultiplier);
      void ApplyVelocity(Vector3 direction, float speed);
      void ApplyMaterial(Material material);
      Vector3 InitialScale { get; }
  }
  ```

### Step 2: Applicator SO 리팩토링
* `MassUnitApplicatorSO.cs`, `VectorUnitApplicatorSO.cs`, `VolumeUnitApplicatorSO.cs`에서 `GetComponent<Rigidbody>` 및 `localScale` 직접 대입 제거 -> `IUnitTargetVisualizer` 메서드 호출로 교체.
