## 2. 문제점 분석 (Code Smells - 5대 기준 위배 상세)

### 2-1. DLV 아키텍처 위배
* **Blind Logic 위배 (물리 컴포넌트 직접 순회):** `UnitChangeService.cs`의 `UpdateCollisionTriggerOwner()`에서 `targetObject.GetComponentsInParent<CollisionDamageTrigger>()`, `GetComponentsInChildren<CollisionDamageTrigger>()`를 직접 호출하여 물리 트리거 소유자를 직접 변경함. 로직 서비스가 유니티 씬 하이어라키를 탐색하는 것은 계층 위배임.

### 2-2. 설계 원칙 위배 (SRP 및 DIP)
* **인터페이스 부재 (DIP 위배):** `UnitChangeService`가 인터페이스 없이 구체 클래스로 직접 주입되고 사용됨.
* **과도한 책임 (SRP 위배):** 단위 해금 검증, 마나 코스트 계산, 파이프라인 연동, 어플리케이터 호출, 충돌체 소유권 강탈 처리가 단일 메서드에 혼재됨.

## 3. 리팩토링 설계 (To-Be Architecture)

```
[L: Logic Layer]
IUnitCatalogService (Interface)
└── UnitCatalogService (해금 상태 및 목록 관리)

IUnitChangeService (Interface)
└── UnitChangeService (단위 변경 판정 및 파이프라인/데이터 갱신)
    └── IOwnershipTransferService (소유권 이전 전담 인터페이스)

[V: Visualizer Layer]
OwnershipTransferVisualizer / TriggerOwnerHandler (컴포넌트 갱신 전담)
```

### 3-1. IUnitChangeService 인터페이스 정의
* DIP를 준수하도록 `IUnitChangeService` 인터페이스 추출 후 VContainer에 바인딩.

### 3-2. 소유권 갱신 책임 분리
* `CollisionDamageTrigger` 소유권 갱신을 `IOwnershipTransferService`로 추상화하여 Visualizer/Physics 영역으로 위임.
